VAULTY 1.0.14 — تقرير المراجعة الأمنية الأولية
================================================

نطاق المراجعة
-------------
- مراجعة ملفات HTML وCSS وJavaScript وService Worker وبيان PWA.
- مراجعة مسار التشفير والتخزين المحلي وفتح الخزنة والاستيراد والاسترداد والقفل.
- فحص نقاط إدخال البيانات ومواضع innerHTML والاتصالات والموارد الخارجية.
- اختبارات ساكنة واختبارات تشفير مستقلة باستخدام Web Crypto في Node.js.

التعديلات المنفذة في 1.0.14
---------------------------
1) تقوية سياسة كلمة المرور الجديدة:
   - الحد الأدنى لكلمة المرور الرئيسية الجديدة أو المعدلة أصبح 12 حرفاً.
   - ينطبق ذلك على إنشاء خزنة جديدة وتغيير كلمة المرور والاستعادة برمز الاسترداد.
   - كلمة المرور الحالية لا تتغير تلقائياً ولا تتعطل الخزائن القديمة؛ يجب فتح الخزنة ثم تغيير كلمة المرور يدوياً.
   - يُنصح بعبارة مرور طويلة وفريدة، لا بمجرد 12 حرفاً متوقعاً.

2) إضافة Content Security Policy داخل index.html:
   - منع تحميل JavaScript من مصادر خارجية.
   - منع object/embed، وتقييد الصور والخطوط والاتصالات إلى موارد محلية/نفس المصدر.
   - الإبقاء على inline styles لأن الواجهة الحالية تحتوي تنسيقات inline.

3) تقوية القفل:
   - عند القفل تُمسح كل حقول input من نوع password، بما فيها حقول النوافذ المغلقة.
   - تستمر إزالة مراجع مفاتيح التشفير والبيانات من حالة التطبيق ومسح شبكة العناصر.
   - هذا لا يضمن مسح الذاكرة الفعلية من محرك JavaScript أو ذاكرة الجهاز.

4) تحسين استرداد الاستيراد:
   - إذا وجدت معاملة استيراد معلقة ولم توجد نسخة الرجوع، يتوقف بدء التشغيل ولا يُسمح بفتح الخزنة من هذه الحالة تلقائياً.
   - لا يتم حذف سجل المعاملة عند فقدان بيانات الرجوع، لتجنب إخفاء حالة غير محسومة.
   - إذا فشل rollback أثناء الاستيراد، تُقفل الواجهة ويُعطّل فتح الخزنة بدلاً من الادعاء بأن البيانات السابقة بقيت سليمة. وإذا كانت المعاملة committed، لا تتم استعادة الخزنة القديمة بالخطأ.

5) تشديد فحص محتوى النسخة الاحتياطية:
   - رفض العناصر ذات الحقول غير المتوافقة أو القيم غير النصية أو الحقول التي تتجاوز الحدود المدعومة قبل استبدال الخزنة.
   - لا يتم تعديل الخزنة الحالية قبل فك تشفير بيانات النسخة والتحقق من محتواها.

نتائج الفحص
------------
- مفتاح التخزين الثابت vaulty_vault_v2 محفوظ كما هو للتوافق.
- تشفير المحتوى الأساسي: AES-256-GCM.
- اشتقاق المفتاح الرئيسي: PBKDF2-SHA256 بعدد 250,000 تكرار في الإعداد الحالي.
- اشتقاق مفتاح الاسترداد: PBKDF2-SHA256 بعدد 600,000 تكرار.
- لا توجد مراجع JavaScript خارجية في HTML.
- لا توجد خطوط أو CSS خارجية؛ الخطوط محلية.
- لم يظهر استخدام eval أو new Function في الملفات المفحوصة.
- القيم النصية التي تدخل في بطاقات الخزنة تمر عبر esc قبل إدخالها إلى innerHTML.
- ملفات JavaScript اجتازت node --check.
- اجتازت فحوصات ساكنة لسياسة CSP، وثبات مفتاح التخزين، وترتيب فك التشفير قبل الاستيراد، ووجود rollback، ومسح حقول كلمات المرور، وتضمين الخطوط المحلية.
- اجتازت اختبارات Web Crypto مستقلة: فك تشفير صحيح، رفض كلمة مرور خاطئة، رفض ciphertext معدّل، والتحقق من اختلاف IV عشوائي بين عمليات التشفير.

ملاحظات ومخاطر متبقية — يجب قراءتها
----------------------------------
1) كلمات المرور الحالية ذات 4 أحرف أو أي كلمة قصيرة تظل كما هي حتى يغيرها المستخدم. يجب تغييرها بعد فتح الخزنة.
2) رمز الاسترداد يختاره المستخدم، والحد الأدنى الحالي 8 أحرف. إذا كان قصيراً أو شائعاً، فقد يكون عرضة لهجوم تخمين دون اتصال على نسخة الاسترداد. اختر رمزاً طويلاً عشوائياً وفريداً واحتفظ به خارج الجهاز.
3) localStorage ليس مخزناً محمياً عتادياً. التشفير يحمي البيانات وهي مقفلة، لكن أي XSS ناجح أو إضافة متصفح خبيثة أو جهاز مخترق قد يسرق البيانات بعد فتح الخزنة.
4) لا يوجد تكامل مع Android Keystore أو Secure Enclave، ولا يوجد تحقق من هوية المواقع لمنع التصيد، ولا مسح تلقائي لمحتوى الحافظة بعد النسخ.
5) PBKDF2 مدعوم ومتوافق مع Web Crypto، لكنه ليس Argon2id. تغيير خوارزمية KDF يتطلب خطة ترحيل واختبارات توافق منفصلة ولا ينبغي تنفيذه عشوائياً.
6) نسخة الاسترداد داخل ملف النسخ الاحتياطي لها تشفير منفصل. فحص الاستيراد الحالي يفك تشفير المحتوى الأساسي بكلمة مرور النسخة؛ أما بيانات الاسترداد فيتحقق من بنيتها فقط لأن رمز الاسترداد غير مطلوب أثناء الاستيراد. يجب تجربة رمز الاسترداد بصورة مستقلة على نسخة اختبار.
7) إذا كان التخزين المحلي ممتلئاً، قد لا تتسع مساحة localStorage لنسخة الرجوع الإضافية؛ عندها يجب أن يفشل الاستيراد قبل استبدال الخزنة. احتفظ دائماً بنسخة احتياطية خارج الجهاز.
8) JavaScript لا يستطيع ضمان محو البايتات من الذاكرة فوراً؛ حذف المراجع والحقول يقلل مدة التعرض لكنه ليس مسحاً جنائياً للذاكرة.

حدود الاختبار
-------------
- هذه مراجعة أمنية أولية للشفرة وليست شهادة أمنية أو اختبار اختراق مستقلاً.
- لم تُجرَ اختبارات على أجهزة Android فعلية، أو WebView مغلف، أو سيناريوهات نظام تشغيل متعددة.
- محاولة تشغيل Chromium headless في بيئة المراجعة انتهت بمهلة زمنية قبل استخراج DOM؛ لذلك لم أعتبرها اختبار تشغيل ناجحاً.
- لم يتم اختبار نسخة المستخدم الحقيقية التي تحتوي على بياناته؛ الاختبارات المشفرة كانت على بيانات اختبار اصطناعية فقط.

التوصية
-------
استخدم هذه النسخة للاختبار ببيانات وهمية أولاً. جرّب إنشاء خزنة، تغيير كلمة المرور، تصدير نسخة، استيراد نسخة صحيحة، كلمة مرور خاطئة، ملف تالف، ورمز استرداد خاطئ. لا تضع كلمات مرورك الأساسية أو بيانات مالية شديدة الحساسية قبل مراجعة مستقلة واختبار فعلي على الجهاز المستهدف.
